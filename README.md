# Pegasus General Store

The official website for **Pegasus General Store** (Pegasus Village Pantry) — North Canterbury's local store. Featuring everyday essentials, artisan foods, local Canterbury produce, and Click & Collect pre-orders.

This guide is written for someone picking this project up for the first time, with no prior knowledge of it. Follow it top to bottom and you should be able to run the site on your own computer.

## What this project is

- A single-page website built with **React + Vite**. That just means: the code in `src/` turns into a website when you run it.
- The live data (products, orders, suppliers, store settings, logins) lives in **Supabase**, an online database service. The site will **not** load without Supabase details — see Step 5. This is important: the old claim that the site runs with “zero external dependencies” is no longer true.
- The current working branch is **`development`**. The `main` branch is an old first commit and does **not** have the latest fixes. Always work on `development` unless someone tells you otherwise.

## What you need before you start

1. **Git** — to download the code and switch branches.
2. **Node.js, version 18 or higher** — this runs the website on your computer. It comes with **npm**, which installs the project's libraries.
   - Check yours by opening a terminal and running:
     ```bash
     node -v
     npm -v
     ```
   - If either command is not found, install Node.js from <https://nodejs.org/> first, then come back.
3. **A code editor** — Visual Studio Code (VS Code) is recommended, but any editor works.
4. **Supabase details** — a Supabase project URL and its public “anon” key (see Step 5). Ask the project owner for these if you do not already have them. **Never use the Supabase “service role” key in this website** — only the anon key.

## Run it for the first time

### Step 1 — Download the code

```bash
git clone https://github.com/kchap225/PEGASUS-General-Store.git
cd PEGASUS-General-Store
```

### Step 2 — Switch to the working branch

```bash
git fetch origin
git checkout development
```

Check you are on the right branch:

```bash
git branch --show-current
git log --oneline -1
```

The first command should print `development`. If it prints `main`, you are on the old code — go back and run `git checkout development`.

### Step 3 — Install the libraries

From inside the project folder, run:

```bash
npm install
```

This downloads several hundred packages. It can take a few minutes the first time, and that is normal. You only need to run it again if `package.json` changes, or if you delete the `node_modules` folder.

Do not edit anything inside `node_modules/` — it is generated by the command above.

### Step 4 — Create your `.env` file

The site reads its Supabase details from a file called `.env` in the project root. That file is deliberately **not** in Git, so you have to create it once per computer.

1. Copy the template file:
   ```bash
   cp .env.example .env
   ```
   On Windows, if `cp` does not work, copy `.env.example` to `.env` in File Explorer instead.
2. Open `.env` in your editor and fill in the two values:
   ```text
   VITE_SUPABASE_URL=https://YOUR-PROJECT.supabase.co
   VITE_SUPABASE_ANON_KEY=YOUR-ANON-KEY-HERE
   ```
3. Where to find them: in Supabase, open your project, go to **Project Settings → API**, and copy the **Project URL** and the **anon / public key**. Paste those in, with no spaces around the `=` sign and no quotes.

**Without this file, or with blank values, the site will fail to load** with an error like `supabaseUrl is required`. That is the first thing to check if you get a blank page.

**Never commit `.env`, and never share its contents in chat, email, or screenshots.** It holds keys for the live project. If you accidentally commit it, tell the project owner straight away so the keys can be rotated.

### Step 5 — Set up Supabase (only if you are using a brand-new Supabase project)

Skip this step if you were given details for the existing Pegasus Supabase project — it is already set up.

If you are starting from an empty Supabase project:

1. In Supabase, open the **SQL Editor** and run the whole file `supabase-setup.sql` from the project root. It is safe to run more than once. It creates:
   - a `suppliers` table,
   - a `store_settings` table (one row, id = 1),
   - a `short_reference` column on the `orders` table,
   - a public `product-images` storage bucket for uploaded product/supplier pictures.
2. The existing `products`, `orders`, and `admins` tables are assumed to already exist in the Pegasus project. If they do not, ask the project owner for the original schema before going further.
3. For Admin access, create a user in Supabase **Authentication**, then set that user's `user_metadata` to include `"role": "admin"`. Without that role, Admin login will sign you straight back out with “This account does not have admin access.” Customer accounts are created from the website itself and get `role: "customer"`.

### Step 6 — Start the website

```bash
npm run dev
```

You should see output ending with a local address, usually:

```text
Local:   http://localhost:5173/
```

Open that address in your browser. You should see the Pegasus homepage.

To stop the server, go back to the terminal and press **Ctrl + C**.

> **Important:** if you change `.env`, you must stop the server (Ctrl + C) and run `npm run dev` again. Vite only reads `.env` when it starts, so editing it while the server is running will not take effect.

## Every time after that

Once the first-time setup is done, the normal routine is just:

```bash
cd PEGASUS-General-Store
git checkout development
git pull
npm run dev
```

Then open <http://localhost:5173>.

## Pages and routes

Once the site is running, these are the main pages:

- `/` — Homepage (Hero, About, product range, suppliers, news, services, contact)
- `/click-and-collect` — Click & Collect pre-orders. A completed order shows a short reference like `PGS-12345 — pickup Tue, 3 Nov · 10:00 AM`. The full order ID is kept in the background and is not shown to customers.
- `/login` — Customer and Admin sign-in
- `/account` — Customer account (when signed in)
- `/admin` — Admin panel (only for accounts with `role: "admin"` in Supabase). Admin tabs are **Products**, **Suppliers**, **Orders**, **Store**, and **Change Password**.

## Contact-form email (Resend)

The "Message us" form on the homepage does not send mail on its own. It posts to a Cloudflare Pages Function at `functions/api/contact.js`, which sends the message via Resend to `shaipat01@gmail.com` and `jim@jwmorentz.com`, with Reply-To set to the customer's email.

Setup (one-time, in the Cloudflare dashboard, not in code):

1. Create a free Resend account and copy its API key. Never put the key in the code, in `.env`, or in Git — it is a secret.
2. In Cloudflare Pages, open the `pegasus-general-store` project → Settings → Environment variables, and add `RESEND_API_KEY` with that key. Redeploy after adding it.
3. Until the sending domain is verified in Resend, mail is sent from `onboarding@resend.dev` and Resend only delivers test mail to the Resend account owner's email. To send to the two addresses above and from `hello@pegasusgeneralstore.co.nz`, verify `pegasusgeneralstore.co.nz` in Resend (Domains → Add a domain) and add the DNS records it gives you in Cloudflare, then set `CONTACT_FROM` to `hello@pegasusgeneralstore.co.nz` in the same Environment variables screen and redeploy.

If the form says it could not send, check Resend → Logs first, then check the Cloudflare variable above is set.

## Click & Collect order emails (Resend)

Order emails use the same Resend account and the same two Cloudflare variables (`RESEND_API_KEY`, `CONTACT_FROM`). No extra setup is needed.

- **When an order is placed** (`functions/api/order-email.js`, type `order-placed`): a confirmation goes to the customer's email, and a notification goes to `shaipat01@gmail.com` and `jim@jwmorentz.com`. The customer email is required on the Click & Collect form, so every new order has one. A failed order email never cancels the order — the customer still sees their PGS reference on screen, with a warning that the email could not be sent.
- **When Admin changes an order's status** (pending, confirmed, ready, collected, cancelled): the customer gets an email for the new status, e.g. "Your order is ready for collection". The status is saved in Supabase even if that email fails, and Admin shows a warning. Orders placed before this was added may have no customer email — those get no status email, and Admin says so.

## Deploy to Cloudflare Pages

This is how the site is published from a local computer. You need a Cloudflare account that has access to the `pegasus-general-store` Pages project. The first time you deploy from a computer, Wrangler (Cloudflare's command-line tool) will ask you to log in to Cloudflare in your browser — follow that prompt once, and later deploys will reuse that login.

**Do these steps in order, from the project folder. Do not skip the build step — Cloudflare deploys the built files, not your source code.**

### Step 1 — Make sure your `.env` is in place

Vite bakes the `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` values into the build at build time. So:

- Your `.env` file must exist and be filled in **before** you build (see Step 4 above).
- If you change `.env`, or change any code, you must build again and deploy again. The old deployment will not pick up the change on its own.
- If you deploy without a valid `.env`, the deployed site will fail to load, just like it does locally.

### Step 2 — Commit first (recommended)

Wrangler will warn you if you have uncommitted changes, because then the deployed site may not match what is in Git. To avoid that confusion, commit your changes on `development` first, then deploy.

If you do want to deploy with uncommitted changes anyway, add `--commit-dirty=true` to the deploy command below to silence that warning.

### Step 3 — Build the site

```bash
npm run build
```

You should see output ending with something like:

```text
✓ built in 924ms
```

That creates/refreshes the `dist/` folder. Do not edit files inside `dist/` by hand — they are regenerated on every build. The `dist/_redirects` file (which makes the site's internal pages like `/click-and-collect` and `/admin` work on Cloudflare) is copied there automatically from `public/_redirects`.

### Step 4 — Deploy the built files to Cloudflare Pages

```bash
npx wrangler pages deploy dist --project-name=pegasus-general-store
```

Notes for a first-timer:

- `npx` downloads Wrangler if it is not already installed, so the first run can take a little while.
- The project name must be exactly `pegasus-general-store`. If you mistype it, Cloudflare will try to create a different project or fail.
- A successful deploy ends with `Deployment complete!` and a link like:
  ```text
  https://10a15336.pegasus-general-store.pages.dev
  ```
  That link is the deployment to check. The part before `.pegasus-general-store.pages.dev` changes with each deploy — that is normal, it is a unique address for that deployment.

### Step 5 — Check the deployed site

Open the link from Step 4 and check the homepage loads, then check at least one other page (for example Click & Collect). If the homepage is blank, the most likely cause is a missing or wrong `.env` at build time — go back to Step 1, fix `.env`, then repeat Steps 3 and 4.

### Deploy checklist (short version)

```bash
git checkout development
git pull
npm install          # only needed the first time, or if package.json changed
npm run build
npx wrangler pages deploy dist --project-name=pegasus-general-store
```

```text
│   │   └── ui/          # Tailwind & Radix UI components
│   ├── data/            # Local JSON seed data (products, suppliers, news)
│   │                    # Used as seed/fallback data; Supabase is the source of truth
│   ├── lib/             # Utility helpers & store metadata (see storeInfo.js)
│   ├── pages/           # Home, ClickCollect, Account, Admin, Login
│   ├── App.jsx          # Application routing
│   └── main.jsx         # React application entry point
├── supabase-setup.sql   # Supabase tables, policies, and storage bucket (see Step 5)
├── .env.example         # Template for .env — copy it, never fill in real keys here

└── vite.config.js       # Vite configuration
```

To change store details that visitors see (address, hours, open/closed status), use the **Store** tab in Admin once the site is running — do not hard-code them in `src/lib/storeInfo.js` unless you know the Admin save is not reaching Supabase.

## Troubleshooting

| Problem | What to check first |
|---|---|
| Blank page, or an error saying `supabaseUrl is required` | You have no `.env` file, or it is blank. Do Step 4, then restart the dev server. |
| Site loads, but products/orders/admin edits do nothing or show errors | Check `.env` values are the right project URL and anon key, and that the Supabase project has the tables from `supabase-setup.sql`. Restart the dev server after fixing `.env`. |
| `git branch --show-current` prints `main` | You are on the old branch. Run `git checkout development` and `git pull`. |
| `localhost:5173` is already in use / port error | Another dev server is still running. Stop it with Ctrl + C in its terminal, or close that terminal, then run `npm run dev` again. |
| Changed code but nothing changed in the browser | Hard-refresh the browser (Ctrl + Shift + R), and check you saved the file and are looking at the right local address. |
| `npm install` fails | Check `node -v` is 18 or higher. If it still fails, delete `node_modules` and run `npm install` again. Do not hand-edit `package-lock.json`. |
| Admin login signs you straight out | That account does not have `user_metadata.role = "admin"` in Supabase Authentication. See Step 5. |
| You edited `.env` but nothing changed | Vite only reads `.env` at startup. Stop the server and run `npm run dev` again. |
| Deployed site is blank, but local site works | The deploy was built without a valid `.env`. Put the right `.env` in place, run `npm run build` again, then deploy again. |
| Wrangler asks you to log in | That is normal the first time on a computer. Follow the browser prompt to log in to the Cloudflare account that owns the `pegasus-general-store` project. |
| Wrangler warns about uncommitted changes | Commit on `development` first, then deploy. Or add `--commit-dirty=true` to the deploy command if you really mean to deploy uncommitted work. |
| Deployed site shows an old version | You probably deployed without rebuilding. Run `npm run build` first, every time, then deploy, and open the new deployment link Wrangler prints — not an old link. |

## Rules for anyone working on this project

1. Work on the `development` branch. Do not push straight to `main`.
2. Never commit `.env`, real Supabase keys, passwords, or tokens.
3. Never use the Supabase service role key in the website — anon key only.
4. Run `npm run lint` before committing, and fix what it reports.
5. If you are unsure what a change does, ask the project owner before pushing it — especially anything touching orders, Admin access, or Supabase policies in `supabase-setup.sql`.
